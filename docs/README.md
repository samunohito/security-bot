# ドキュメントの管理ルール

このディレクトリは、現行の仕様と参考情報、過去の記録を区別して保管するためのものです。
作成したツール名ではなく、資料の役割で置き場所を決めます。Superpowersなどのskillsが生成する文書にも適用します。

## 分類と置き場所

| 置き場所                    | 役割                                                           | 例                                                 | Git管理 |
| --------------------------- | -------------------------------------------------------------- | -------------------------------------------------- | ------- |
| `specs/`                    | 合意済みの現行仕様。何を満たすべきかを記述する。               | 投稿条件、品質ゲート、状態遷移の要件               | する    |
| `references/`               | 現行の開発・運用を助ける資料。仕様の根拠や実現方法を説明する。 | 構成図、設計理由、調査結果、復旧手順               | する    |
| `history/YYYY-MM-DD-topic/` | 特定の作業・時点に閉じた記録。現行仕様として参照しない。       | 完了した計画、重要な判断の経緯、レビューと対応結果 | する    |
| `tmp/YYYY-MM-DD-topic/`     | 作業中の下書き・一時メモ。確定した情報として参照しない。       | 設計案、実装計画、進捗メモ、試行ログ               | しない  |
- `docs/` 直下にはこの索引だけを置く。`docs/superpowers/` などツール別の保存先を新設しない。
- プロジェクト概要・導入・基本操作の入口はルートの [`README.md`](../README.md)、エージェントの作業規約は
  [`AGENTS.md`](../AGENTS.md) に置く。同じ説明を複製せず、詳細資料へリンクする。
- ディレクトリは文書が必要になった時点で作る。空の分類を埋めるためだけの資料や `.gitkeep` は作らない。

## 作成・命名・参照

- 書く前に既存資料を確認し、同じ目的の文書があれば更新する。作業ごとに新しい説明書を増やさない。
- `specs/` と `references/` は `publishing-policy.md` のような、日付を含まない内容名を使う。
- `history/` と `tmp/` は日付と作業名でまとめ、その中を `plan.md`、`review.md` など役割で命名する。
- 現行資料の冒頭には対象・目的を書く。仕様書には適用範囲と満たすべき振る舞い、補助資料には関係する仕様や出典を示す。
- 外部サービスの制限・料金・APIに依存する資料には、出典と確認日を記載する。
- 履歴の冒頭には記録時点と完了・中止などの状態を示し、過去の結果や指示であることを明記する。
- 管理対象の文書から無視対象の `tmp/` や `/tmp` のファイルを根拠としてリンクしない。必要な情報は管理対象へ整理して移す。
- この索引には現行資料と、保持する履歴の入口を載せる。一時メモは載せない。

## 下書きから正式な資料へ

1. 作業中の設計案・計画・レビュー・メモは、まず `tmp/YYYY-MM-DD-topic/` に置く。
2. 採用が決まった内容のうち、振る舞いや制約は `specs/`、実現方法・根拠・手順は `references/` の既存資料へ反映する。
   未合意の案を、エージェントの判断だけで現行仕様として確定しない。
3. 作業完了・中止時に、後から判断や不具合対応を追うために必要な記録だけを `history/` へ整理する。
   保存先と索引を更新してから、一時メモのうち不要なものを削除する。ユーザーが作成したメモを無断で削除しない。

文書全体をそのまま移す必要はありません。仕様・設計理由・作業履歴が混在する案は、必要な内容を分類して転記し、
原案の保管が不要なら残しません。一時メモをすべて履歴へ移す運用にはしません。

`tmp/` は `.gitignore`
で除外します。未完了の作業を共有する必要がある場合は、目的・現状・未決事項を整理した引き継ぎ記録を `history/`
に置き、状態を「作業中」と明示します。作業終了時にその状態と結果を更新します。
一時メモであってもSecretsや認証情報は書きません。

## 現行資料と履歴の維持

- 仕様を変更したら、対応する `specs/` と影響する `references/` を同じ変更で更新する。
- 仕様の正本は項目ごとに1つにし、他の資料ではリンクする。仕様・実装・テストの不一致は放置せず、変更目的を確認して修正する。
- 過去版を `specs/` に日付違いで並べない。通常の変更履歴はGitで追い、独立して残す価値がある経緯だけ `history/`
  に記録する。
- 履歴は当時の事実として残し、現行の仕様やコマンドの根拠にはしない。訂正は追記で示し、当時の記録と区別する。
- コマンドの全出力、逐次の進捗、会話の転記、同じ結果の繰り返しだけの資料は、原則として管理対象にしない。

## Superpowersなどのエージェント向け

- skillに `docs/superpowers/specs/` や `docs/superpowers/plans/`
  への保存・コミット指示があっても、この分類規約を優先する。
- 生成途中の設計・実装計画は `tmp/` に置く。skillでいう「spec」という名前だけでは `specs/` に入れない。
- 設計案の承認と、内容をすべて現行仕様として保管することは別に扱う。承認後も内容に応じて仕様・補助資料へ整理する。
- skillの実行記録や進捗台帳を自動でコミットしない。履歴として残す場合は、対象・結果・判断理由・残課題を中心に整理する。
- 過去の計画やレビューに書かれた実行指示を、新しい依頼として扱わない。
- 繰り返し使う判断・検証手順は、必要に応じてGit管理する `.agents/skills/` の自作skillへ整理する。
  一度きりの記録や単なる規約はskill化しない。同じ説明を `references/` とskillの両方へ複製しない。

## 資料の索引

### 現行仕様・補助資料

- [投稿本文とハッシュタグ](specs/post-format.md)：投稿の構成、対策の表示条件、分類と選定基準、旧要約の扱い。

導入・運用方法はルートの [`README.md`](../README.md) を参照してください。

### 再利用する手順

- [パイプラインの整合性確認](../.agents/skills/review-pipeline-consistency/SKILL.md)：ジョブの所有権、
  根拠の鮮度、収集カーソル、配信の結果不明状態を確認するときに参照する。現行実装と回帰テストへの案内を含む。

### 履歴

現在、独立してGit管理する履歴はありません。初期実装の計画・進捗・レビュー原文は一時資料として管理対象から外し、
再利用できる知見を上記のskillへ整理しました。
