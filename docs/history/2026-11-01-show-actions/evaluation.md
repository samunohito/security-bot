# 対策の表示を分類から切り離した変更と再生比較

2026-11-01実施、実装・検証完了。[Issue #18](https://github.com/samunohito/security-bot/issues/18)の記録。
基点はPR #17マージ後の`60ae5a8961a607c780e99ac0a3927e92c82986a9`。
現行の振る舞いは[投稿本文の仕様](../../specs/post-format.md#対策の表示)を参照する。

## 変更と範囲

共通のformatActionからactionKindの表示条件を削除し、actionがあれば「対策: …」を表示する。
通常更新も個別・まとめで表示し、使用中止などの重要な指示を誤分類で消さない。
nullの対策を補完せず、既存のエスケープと文字数判定を使う。

actionKind・保存形式・モデル・生成と検品のプロンプト・タグ・入力生成・検証器は変更していない。
分類を廃止する変更や、文中の特定語を探して例外表示を救済する規則は追加しない。
正しい対策の表示と、生成内容の正しさは独立した問題として扱う。

既存の検証済み要約は新しい整形規則で準備される。分類が欠落・nullの旧要約も、既存actionがあれば表示する。
保存済みのまとめ本文は既存の本文を再利用し、一括再整形・再送はしない。
短縮キャッシュ、unknownの自動再送禁止、配信・予算・冪等性の処理は変更していない。

## 固定した72応答の表示比較

前回と同じ6資料・72応答のうち、構造成功68件を再生成せず整形した。
変更前の個別本文が保存案と一致し、変更後も対策行以外の内容が不変であることを確認した。
まとめ項目でも対策行以外は不変。全件で入力生成と機械検査が保存記録と一致した。
生成・意味検証・短縮・配信の新規LLM/API実測ではない。

| 指標                               | 変更前 | 変更後 |
| ---------------------------------- | -----: | -----: |
| 構造成功・整形対象                 |     68 |     68 |
| 対策行を表示する要約               |     20 |     46 |
| 対策のある要約のうち表示される件数 |  20/46 |  46/46 |
| KEVの使用中止条件が表示される件数  |   3/12 |   6/12 |
| 機械検査の通過                     |     43 |     43 |
| 素の個別本文が500文字以内          |     68 |     68 |

新たに対策が表示される26件の内訳はVisual Studio 2件、JVN 6件、KEV 9件、Thrift 9件。
KEVのLuna high 3件は要約に保持していた使用中止条件を表示へ戻せた。
回復3件のうち、厳格ゲートで情報充足と判定されていたのは試行3の1件だけ。
試行1・2は情報不足もあるため、3件の表示回復を3件の掲載回復とは扱わない。
一方、LlamaのKEV 6件は生成時点で条件がなく、変更後も表示にない。
Thriftの正しい0.24.0への通常更新も9件で表示されるが、3件の影響文に残る「以前」という境界の誤りは直っていない。

個別本文の増分は最大92コードポイント、まとめ項目の増分は最大91コードポイント。
この資料群の素の個別表示は前後とも全68件が500文字以内だった。
これは保留された要約も含む整形比較であり、68件の投稿が許可される意味ではない。
まとめの文字数は固定の理由・スコアで項目を整形した値で、実運用の掲載・分割数の推定には使わない。
同じ6記事の反復とLunaの別ハーネス近似を含むため、一般の品質・成功率やモデル順位を主張しない。

## 限界とトレードオフ

既存検品を通った誤生成も新たに表示され得る。
Visual StudioのLlama上限導入前・試行2は、対策記載のない原文から「更新する」を補い、
機械・意味・情報充足の検査を通っていた。この1件は変更後に「対策: 更新する」と表示される。
別の試行1の「未提供」も表示案に現れるが、こちらは捏造引用などで機械検査が保留している。
本変更が情報の正しさを改善したと解釈せず、意味検証・生成の後続評価へ残す。

長くなれば既存の個別短縮・まとめ分割が発生し、場合によっては保留が増える。
統合テストの400文字上限・6項目では、対策追加により3件ずつの2分割から2件ずつの3分割になった。
各項目の対策を維持し、全分割が上限内で全CVEを一度ずつ保持することを確認した。

整形処理は対策行を文字数目的で落とさないが、LLMの短縮自体による欠落は別の問題。
厳格ゲートはaction:nullの短縮を情報不足として止める。
品質ゲート無効の投稿先では、引用・意味検査が合格した不完全な短縮要約を許す従来挙動を維持するため、
対策が欠ける場合がある。検査の緩和設定を変えず、この変更の保証範囲を文書化した。
短縮後に非nullの対策から条件の一部だけが落ちる問題も、既存の意味検証が必ず発見できるとは保証しない。

## テスト・確認

- 変更前は20ファイル・497テスト合格。
- 新しい期待で通常更新・旧要約・使用中止・対策のエスケープ・通常更新の追加だけで短縮が必要になる条件を実行し、
  18件が期待どおり失敗したことを確認してから表示処理を変更した。
- 関連137テスト合格。新規生成の分類必須、短縮時の引用不正・意味不支持・再短縮しても上限超過の保留を確認した。
  短縮後に分類がroutine_updateでも対策を表示し、再送準備で同じ短縮結果を再利用する。
- 独立レビューで分類・CVEの有無・新規/更新/訂正の42条件、エスケープ、文字数境界、
  キャッシュ・緩和ゲートの挙動を確認。製品コードの阻害指摘はなく、文書2点を修正した。
  再確認で未解消指摘0件。72応答の文字数・表示ハッシュ・集計も独立に再計算して全件一致した。
- CodeRabbitは全11変更ファイルをレビューし、指摘0件で完了した。
- 最終の全体510テスト、typecheck、format:check、build（dry-run）、CLI config validateはすべて合格した。

依存復元時、npm ciはpackage-lock.jsonがないため実行できなかった。
実際のリポジトリはpnpm 12.15.0 / pnpm-lock.yamlで、固定lockfileで復元した。
通常の隔離配置では既存tsconfigのvite/client参照が解決しないことを確認し、
同じlockfileの`pnpm install --frozen-lockfile --shamefully-hoist`で、既に依存しているViteの型をルートから参照可能にした。
その環境ではnpm run typecheckも合格した。package.json・lockfile・tsconfig・依存バージョンは変更していない。
これは開発環境の配置条件であり、通常のpnpm復元だけでtypecheckが成功したという記録ではない。
