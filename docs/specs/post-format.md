# 投稿本文とハッシュタグ

広いセキュリティ動向を流し読みし、関心のある分野・技術テーマ・メーカー・製品の投稿を探すための仕様。
利用製品の事前登録は要求しない。

個別・まとめの選択と掲載条件は[発信方法と掲載理由](publishing-policy.md)に従う。
まとめ投稿は検証済みの個別項目を箇条書きで並べ、期間・分割番号と共通の `#NVD` を付ける。
個別項目の製品タグはまとめ全体へ付けない。

## 要約・検品に渡す根拠

生成・検品・短縮は共通の入力生成処理を使う。情報源は最大4件とし、1件につき本文抜粋は最大1,000文字、
影響範囲・被害・対策の各節は最大400文字、抜粋合計は最大2,200文字とする。

原文に存在する抽出済みの値を優先する。複数CVEなどのarticle形式で節が空の場合は、保存本文の見出しから補う。
対象CVEを明記する行と後続の説明・箇条書きを優先し、別CVEから始まる項目や次の見出しを越えない。
対象CVEのない節は、他CVEの記載もない場合に限り記事共通の参考情報として渡す。
日英の既存見出しと「緩和策」、番号付き見出しを扱う。
未知の番号付き行は次の見出しとして扱うため、平文で見出しと区別できない番号付き手順は補完範囲から外れる場合がある。

抜粋は保存原文の連続範囲に限り、正規化・翻訳・離れた箇所の連結はしない。
400文字を超える節は行末・文末で切り、収まる区切りがなければnullにする。
設定値の引用符・括弧内では切らず、上限判定では行末の改行文字を除く。
対応する節がなければ本文抜粋とnullを維持し、全文送信や追加のLLM呼び出しへは切り替えない。

補完した候補によってscopeや集計属性を変えず、記事共通の対策を対象CVEへの帰属確認済みとして扱わない。
意味検証、品質ゲートは引き続き必要とする。

### 引用の送信範囲と対象への帰属

引用は、保存原文に実在し、実際に送った単独のtextまたはsection内に連続して存在する必要がある。
本文と別の節を連結した引用、抜粋の外や5件目の情報源だけにある引用を受理しない。
この検査はcve・articleの両scopeに適用する。引用の原文位置は内部で保持し、Summaryの保存形式は変更しない。

articleで対象CVEを扱う場合は、保存全文の行・項目構造から帰属範囲を求める。抜粋の切断位置から推測しない。
箇条書き・項目番号を除いた対象CVE単独の行、または対象CVEとコロンで始まる項目ラベルは、
続く通常行・箇条書きまで同じ対象の説明として扱う。CVEを囲む閉じ括弧も許容する。
その範囲に収まる引用自体にはCVE番号を要求しない。
対象CVEを含む自然文行も、別CVEの明確な項目内でなければ同一行だけを根拠にできるが、後続行へ帰属を継承しない。
CVEで始まる自然文も同じ扱いとし、別CVE項目の帰属を解除する新しい項目ラベルとはしない。

空行、既知の見出し、ATX形式のMarkdown見出し、未知の番号付き見出し、次のCVE行で継承を止める。
CVE項目内の混在行や他CVEへの言及も継承を止め、次の明確な対象項目まで対象帰属を再開しない。
対象CVEの自然文を挟んでも、明確な項目への所属を忘れず、後に他CVEが言及された場合は保留する。
他CVEで始まる行は自然文か項目か区別できなくても、安全側に別項目として扱う。
この後の対象への自然文の言及は、空行・見出し・明確な対象ラベルまで保留するため、正しい独立段落も拒否する場合がある。
明確なCVE項目外で、CVE番号が文中にある独立した自然文の列記からは、次の自然文行へ制約を持ち越さない。
別CVE項目内の対象参照、CVE番号の前方一致、共通節は対象への帰属を確定しない。
見出しか手順か区別できない番号付き行は保留する。強調やSetextなど、認識しない見出し形式は境界にできない。

同じ引用文字列が送信候補の対象・非対象の両方に一致する場合は保留する。
同じ原文位置をtextとsectionで重複送信しただけの場合や、未送信箇所に同文があるだけの場合は曖昧としない。
抽出済みの節は原文の全一致位置を候補にし、最初の一致だけで帰属を決めない。

この照合は、引用の送信範囲と局所的な項目帰属を検査するもの。
自然文の暗黙の参照、複数CVEに共通する対策、設定名と値の対応、バージョン境界や必要権限の意味までは保証しない。
正しい対策でも構造から対象を確定できなければ保留し、番号の必須条件を単純に削除して救済しない。
生成・診断・短縮は同じ照合を使い、合格後も別推論の意味検証と既存の厳格ゲートを通す。
既存の検証済みSummaryキャッシュは従来どおり扱い、一括再評価・再生成・再送は行わない。

## NVD Highのまとめ項目

基本となる4行は次のとおりとし、存在する対策・未確認事項の行を追加する。項目の間にだけ空行を入れる。

```text
・CVE-2026-119205｜新規｜CVSS 7.1
pypdf：pypdfの無限ループの脆弱性
影響: クラフトされたサイクルDictionaryObjectの複製時に無限ループが発生する可能性
https://nvd.nist.gov/vuln/detail/CVE-2026-119205
```

- CVE・掲載理由・CVSSを先頭行、対象名と概要を次の行にまとめる。対象名と概要が同一なら重複させない。
- 全項目に共通する `[High]` と `出典:` は省く。影響の成立条件・権限・重要なバージョン境界は省略しない。
- 対策・未確認事項がある場合は、影響と出典の間へ各1行追加する。通常更新も表示し、複数の出典URLも別々の行で残す。
- 旧要約の対象名は元の見出しで代替する。概要・影響が未確認なら、その状態を明示する。
- 項目内には空行や製品タグを付けず、本文のエスケープ規則は個別投稿と共通にする。
- 分割基準は投稿先ごとの `targets.maxCharacters` とし、期間・分割番号・URL・共通の `#NVD` を含む
  投稿全体のUnicodeコードポイント数で判定する。件数を4件などに固定せず、上限に収まる項目を順番に詰める。
  項目を途中で切らないため、最後の分割などは上限未満になる。

## 個別投稿の構成

```text
[High] CVE-2026-97860
ヤマハ YMS-VPN8／YMS-VPN8-CP
Windowsサービスのファイルパスの引用符不備

影響: システムドライブへの書き込み権限を持つユーザーにより、SYSTEM権限で任意のコードが実行される可能性があります。

出典: https://jvn.jp/jp/JVN30675482/

#ネットワーク #パス処理 #ヤマハ #YMS_VPN8 #YMS_VPN8_CP
```

- CVEがある場合のみ、深刻度とCVEを先頭行に置く。記事内の別CVEの深刻度を転用しない。
- 対象名と問題の見出しは各1行とし、概要の重複を避ける。
- 見出し・影響・対策・未確認事項・出典・タグの間は空行で区切る。該当しない段落は省く。
- CVEがない場合は内部の情報源キーや深刻度を表示せず、対象名から始める。
  影響の段落がある場合も「影響:」を付けず、説明文として表示する。
- 更新・訂正は、先頭にそれぞれ `[更新]`・`[訂正]` を付ける。既存投稿への参照も維持する。
- 影響の成立条件、必要な権限、重要なバージョン境界を短縮のために省かない。
- CVEの影響が未確認の場合は「影響: 未確認」とし、判断に関係する未確認事項も維持する。

## 対策の表示

通常更新も含めて、検証済み要約のactionが存在する場合は「対策: …」として表示する。
個別・まとめで同じ規則を使い、actionKindによって表示を省かない。
対策がnullの場合は段落を出さず、分類から「未提供」などの文言を補完しない。
本文は既存のエスケープを適用し、改行を空白へまとめる。

actionKindは保存互換と対策内容の検証のため維持し、次のように分類する。

| 種別               | 対策の内容                                 |
| ------------------ | ------------------------------------------ |
| `routine_update`   | 通常の更新指示や具体的な中身のない対策案内 |
| `unpatched`        | 修正版が未提供であること                   |
| `workaround`       | 機能の無効化など、具体的に実行できる回避策 |
| `additional_steps` | 鍵の交換など、更新以外にも必要な作業       |
| `patch_warning`    | 一部バージョンが未修正など、修正版の注意点 |

通常の更新指示は `routine_update` とする。
「アップデート、またはワークアラウンドを実施」のように回避策の内容がない定型文もこれに含める。
修正版の有無が未確認であることを「未提供」と断定しない。
通常更新と例外が併記される場合は例外を優先し、その内容を本文に含める。

表示を分類から切り離しても、新規生成・短縮での種別必須、引用・意味検証と品質ゲートは維持する。
厳格な品質ゲートでは従来どおり概要・影響・対策が揃い、未確認事項がないことを要求する。
旧要約のactionKindが欠落・nullでも、既存actionがあれば表示する。
送信済み投稿や保存済みのまとめ本文を一括変更・再送するものではない。

対策を含む本文全体で文字数を判定し、個別投稿は既存の短縮・再検証、まとめ投稿は既存の分割を行う。
短縮・分割後も上限に収まらなければ従来どおり保留する。整形処理は対策行だけを削って収めない。
LLMによる短縮結果自体で対策がnullになった場合、厳格ゲートでは情報不足として保留する。
品質ゲートを無効にした投稿先では、従来どおり不完全な短縮要約も検査合格なら許可するため、対策が欠ける場合がある。
この表示変更だけで、生成・短縮時点の条件欠落や検品の見逃しを防げるものではない。

## タグの分類と選定

LLMは引用付きのタグ候補を合計最大6個返す。生成プロンプトとJSON Schemaの配列上限を揃え、同じタグを繰り返させない。
上限を超える応答は構造不正として扱い、JSONの修復や候補の切り捨てで救済しない。
プログラムが構造・分類・名称を検査した後、投稿時のタグ表記で重複を除き、
分類ごとに候補の先頭から上限内で採用する。重複は枠を消費しない。
採用したタグと本文を引用照合し、既存の別推論による意味検証にも渡す。候補合計が6個以内なら分類ごとの個数超過は選別で整理する。
用途は最大1個、テーマは最大2個、メーカーは最大1個、製品は最大2個、合計最大6個とする。
該当する候補がなければ選ばず、「その他」で埋めない。

この整理は新規要約、管理APIによる再生成、文字数超過時の短縮生成に適用する。
既存の保存済み不合格要約・保留配信は自動で変更・再送しない。

### 用途

動作環境より対象製品の主な用途を優先する。

| タグ            | 選定基準                                                  |
| --------------- | --------------------------------------------------------- |
| `#ネットワーク` | VPN、ルーター、DNS、プロキシなど                          |
| `#OS`           | OS本体、カーネル、ドライバー。OS上の一般アプリは含めない  |
| `#ブラウザ`     | ブラウザ本体と拡張機能                                    |
| `#業務アプリ`   | グループウェア、文書管理、業務システム                    |
| `#Web基盤`      | Webサーバー、CMS、Webフレームワーク                       |
| `#開発ツール`   | IDE、ビルドツール、パッケージ管理                         |
| `#クラウド基盤` | 仮想化、コンテナ、クラウド管理                            |
| `#データベース` | DB本体と管理ツール                                        |
| `#組み込み機器` | IoT、家電、産業機器。主用途がネットワークならそちらを優先 |

### 技術テーマ

問題の原因や成立条件に直接関係する場合だけ選ぶ。

| タグ                | 選定基準                                           |
| ------------------- | -------------------------------------------------- |
| `#認証`             | 本人確認、ログイン、セッション管理の問題           |
| `#アクセス制御`     | 権限チェックの不備、本来許されない資源へのアクセス |
| `#暗号`             | 暗号方式、鍵、証明書検証そのものの問題             |
| `#メモリ安全性`     | バッファオーバーフロー、解放後使用など             |
| `#インジェクション` | SQL、コマンド、スクリプトなどの不正な解釈・実行    |
| `#パス処理`         | パストラバーサル、ファイルパスの解釈の問題         |
| `#サプライチェーン` | 配布物、依存関係、更新経路の侵害                   |

VPNが暗号を使うという理由で暗号タグを付けたり、任意コード実行という被害だけから
インジェクションと判断したりしない。依存ライブラリの通常の脆弱性だけではサプライチェーンとしない。

### メーカー・製品

出典の引用に現れる対象名を抽出し、企業名の翻訳・別名・略称を推測しない。
多数の製品を含む場合は、出典に明示された製品群の名前を優先する。
名前が似ているだけで別製品を同一の製品群としてまとめない。

抽出名称はUnicode NFKCで正規化し、英字を大文字へ、記号や空白の並びを `_` へ変換する。
ただし `+` は `_PLUS`、`#` は `_SHARP` とし、`C++` と `C#` を区別する。
例：`YMS-VPN8` は `#YMS_VPN8`、`Acme Server` は `#ACME_SERVER`。
固定分類の表記は変えない。用途・テーマ・メーカー・製品の順で末尾に並べ、重複は除く。
メンションやMFMを含む不正な名称、数字だけのタグは出力しない。

## 根拠・保存形式との互換性

対象名と各タグは概要などと同じ形式の引用を持つ。引用の実在、数値、複数CVEの記事での対象帰属を検証する。
メーカー・製品名は引用内に存在することも検証する。分類の意味、対象との関係、対策種別、
影響条件の保持は既存の意味検証で確認する。

追加フィールドのない保存済み要約も読み込めるようにする。
旧要約は自動で再生成せず、対象名は元の見出しで代替する。
タグがなければ補完せず、対策は種別の有無にかかわらず既存actionがある場合に表示する。
新しい対象名・分類は新規に生成する要約から反映する。
新規生成・再生成・短縮の結果では、対策本文があるのに対策種別が欠けた要約は保留する。
この本文仕様自体は、改訂・配信・予算の状態遷移を定めない。

## Misskeyへの送信

本文中の任意タグ・メンション・MFMはエスケープし、検証済みの末尾タグだけをタグとして出す。
タグ抽出は有効にするが、メンションと絵文字の自動抽出は無効のままとする。
文字数制限は参照URLを含む投稿全体に適用し、短縮時にも同じ根拠・品質検証を行う。

Misskeyの抽出制御は2026-10-28に[公式のnotes/create実装](https://github.com/misskey-dev/misskey/blob/develop/packages/backend/src/server/api/endpoints/notes/create.ts)で確認。
Workers
AIへの構造化出力指定は既存の[JSON Mode](https://developers.cloudflare.com/workers-ai/features/json-mode/)を継続利用する（同日確認）。
